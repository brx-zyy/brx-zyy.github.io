# Web API Fundamentals

An **API (Application Programming Interface)** is a way for different applications or services to communicate with each other. In a web application, the API usually sits between the client and the backend, receiving requests, processing them, and sending back a response.

For example, when you log in to a website, the frontend might send your username and password to an API endpoint. The backend processes the request, checks the credentials, and returns a response telling the application whether the login was successful.

APIs are everywhere in modern applications. They are used for authentication, user accounts, payments, databases, mobile applications, third-party integrations, and communication between different backend services.

From a security perspective, understanding how APIs work is important because the API often exposes a large part of an application's functionality. Things like authentication, authorization, input validation, and access to sensitive data are handled through API requests.

The goal of this section is to understand how APIs are designed, how requests and responses work, and how the different components fit together.

> **Understand the API → understand how the application works → understand the attack surface.**

---

## 1. The Big Picture

A Web API is the communication layer between a client and backend systems.

```text
CLIENT
  │
  │ HTTPS
  ▼
API GATEWAY / WAF
  │
  ▼
API SERVER
  │
  ├── Authentication
  ├── Authorization
  ├── Input Validation
  └── Business Logic
  │
  ▼
DATABASE
  │
  ▼
API SERVER
  │
  │ JSON / HTTP Response
  ▼
CLIENT
```

Think of every API request as:

```text
Request
   ↓
Transport
   ↓
Gateway
   ↓
API
   ↓
Identity
   ↓
Permissions
   ↓
Logic
   ↓
Data
   ↓
Response
```

# 2. The Client

The **client** is whatever communicates with the API.

```text
Browser
Mobile App
Desktop Application
JavaScript Frontend
IoT Device
```

Example:

```http
GET /api/users/1 HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Accept: application/json
```

The client normally **does not talk directly to the database**.

```text
Client
  ↓
API Server
  ↓
Database
```

This gives the backend control over authentication, authorization, validation, and business logic.

# 3. HTTP / HTTPS

APIs commonly communicate over **HTTP or HTTPS**.

```text
HTTP
 ↓
Application-layer communication

HTTPS
 ↓
HTTP + TLS
```

An HTTP request can contain:

```text
Method
URL / Endpoint
Headers
Cookies
Parameters
Body
Authentication
```

Example:

```http
GET /api/users/1 HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Accept: application/json
```

### Remember

```text
Content-Type
    ↓
"What am I sending?"

Accept
    ↓
"What do I want back?"
```

# 4. Endpoints

An **endpoint** is a URL used to interact with an API resource or operation.

```text
/api/users
/api/users/123
/api/products
/api/orders
/api/payments
```

### Collection

```text
/api/users
```

A collection of users.

### Individual Resource

```text
/api/users/123
```

User `123`.

### Subcollection

```text
/api/users/123/orders
```

Orders belonging to User `123`.

---

# 5. HTTP Methods & CRUD

HTTP methods describe the requested operation.

| Method   | Purpose          |
| -------- | ---------------- |
| `GET`    | Read             |
| `POST`   | Create / Action  |
| `PUT`    | Replace / Update |
| `PATCH`  | Partial Update   |
| `DELETE` | Delete           |

The common CRUD mapping:

```text
POST    → CREATE
GET     → READ
PUT     → UPDATE
DELETE  → DELETE
```

But APIs aren't limited to CRUD.

```http
POST /users/1/activate
POST /orders/10/refund
POST /password/reset
```

These are **actions**.

> Don't assume an endpoint's behavior from its HTTP method alone.

Think of the gateway as the **front door** of the API.

```text
CLIENT
  ↓
WAF
  ↓
API GATEWAY
  ↓
API SERVER
```

### API Gateway

Common responsibilities:

```text
Routing
Rate Limiting
Authentication Integration
Traffic Control
Load Balancing
```

### WAF

Primarily focused on:

```text
Request Inspection
Filtering
Malicious Traffic Detection
Web Attack Protection
```

They can exist separately or be combined.

### Routing

```text
/api/users
     ↓
User Service

/api/orders
     ↓
Order Service

/api/payments
     ↓
Payment Service
```

### Rate Limiting

```text
Client
  ↓
Rate Limiter
  ↓
Too many requests?
  ↓
429 Too Many Requests
```

# 7. API Server

The API server is where the backend processes the request.

A simplified decision flow:

```text
Request
  ↓
Who is making it?
  ↓
Is the credential valid?
  ↓
What are they allowed to access?
  ↓
Is the input valid?
  ↓
What does the business logic allow?
  ↓
What data is required?
  ↓
Build response
```

The server commonly handles:

```text
Authentication
Authorization
Input Validation
Business Logic
Database Queries
Response Generation
```

# 8. REST

**REST** stands for:

> Representational State Transfer

REST is an **architectural style**, not a protocol.

REST commonly models APIs around resources:

```text
/users
/products
/orders
/payments
```

Example:

```http
GET /api/users/1
```

> Give me User 1.

### REST Constraints

The important constraints are:

```text
Uniform Interface
Client-Server
Stateless
Cacheable
Layered System
Code on Demand (optional)
```

### Stateless

Each request should contain the information necessary for the server to process it.

```http
GET /api/users/1
Authorization: Bearer <token>
```

Then:

```http
GET /api/users/1/orders
Authorization: Bearer <token>
```

Each request carries what the server needs.

### Cacheable

Responses can be cached to reduce:

```text
Latency
Server Processing
Database Queries
Network Traffic
```

Example:

```http
Cache-Control: max-age=3600
```

### Layered System

The client doesn't need to know the internal backend architecture.

```text
Client
  ↓
Gateway
  ↓
API Server
  ↓
Microservice
  ↓
Database
```

### Code on Demand

Optional REST constraint where a server can provide executable code to the client.

```text
Server
  ↓
JavaScript
  ↓
Browser
```

# 9. GraphQL

GraphQL is a **query language and API approach** where the client specifies the data it wants.

The easiest comparison:

```text
REST
 ↓
"Give me this resource."

GraphQL
 ↓
"Give me these fields."
```

Example:

```graphql
query {
  user {
    id
    username
    email
  }
}
```

GraphQL commonly uses a single endpoint:

```text
/graphql
```

Example:

```http
POST /graphql HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Type: application/json
```

### Query


### Mutation

### Subscription

# 12. Authentication

Authentication answers:

> **Who are you?**

Example:

```http
Authorization: Bearer <token>
```

The server validates the credential and identifies the user.

If authentication fails:

```http
401 Unauthorized
```

Keep this distinction clear:

```text
Authentication
      ↓
"Who are you?"

Authorization
      ↓
"What can you access?"
```

---

# 13. Authentication Methods

Common approaches include:

```text
Basic Authentication
API Keys
JWT
HMAC
OAuth 2.0
No Authentication
```

---

## Basic Authentication

Credentials are sent using the `Authorization` header:

```http
Authorization: Basic <credentials>
```

Conceptually:

```text
username:password
       ↓
    Base64
       ↓
Authorization Header
```

### Important

```text
Base64 ≠ Encryption
```

Basic Authentication should therefore be protected with HTTPS/TLS.

---

## API Keys

An API key is a value issued by an API provider.

```text
Register
   ↓
Receive API Key
   ↓
Send Key
   ↓
API validates it
   ↓
Allow / Deny
```

It may appear in:

```http
API-Key: YOUR_KEY
```

or:

```http
GET /api/users?apikey=YOUR_KEY
```

Keys can leak through:

```text
Source Code
Git Repositories
Configuration Files
Logs
URLs
Screenshots
Traffic
```

> **Treat API keys as secrets unless explicitly documented otherwise.**

# 14. JWT

JWT = **JSON Web Token**

A common flow:

```text
Credentials
    ↓
API Server
    ↓
Verify
    ↓
Generate JWT
    ↓
Return Token
    ↓
Future Requests
```

Example:

```http
Authorization: Bearer <JWT>
```

### JWT Structure

```text
HEADER.PAYLOAD.SIGNATURE
```

Think:

```text
┌───────────────┐
│    HEADER     │
├───────────────┤
│    PAYLOAD    │
├───────────────┤
│   SIGNATURE   │
└───────────────┘
```

### Header

```json
{
  "alg": "HS512",
  "typ": "JWT"
}
```

### Payload

Contains claims:

```json
{
  "sub": "1234567890",
  "name": "user1",
  "iat": 1516239022
}
```

Claims can include:

```text
User ID
Username
Issuer
Expiration
Issued At
Roles
Permissions
```

### Critical

> **JWT payloads are normally encoded, not encrypted.**

Therefore:

```text
JWT ≠ Encryption
```

Don't place sensitive secrets in a JWT payload simply because it is encoded.

### Signature

Conceptually:

```text
Header
   +
Payload
   +
Secret / Private Key
   ↓
Signature
```

The server verifies the signature before trusting the token.

### JWT Security

Security depends heavily on implementation.

Pay attention to:

```text
Algorithm Validation
Signature Verification
Signing Secrets
Expiration
Token Storage
Sensitive Claims
Authorization
```

---

# 15. HMAC

HMAC = **Hash-based Message Authentication Code**

Basic idea:

```text
Request Data + Secret
        ↓
       HMAC
        ↓
     Signature
```

The server calculates the expected value using its secret.

```text
Received Request
      ↓
Calculate HMAC
      ↓
Compare
   ↙       ↘
Match     Mismatch
  ↓           ↓
Accept       Reject
```

HMAC provides a mechanism for verifying **integrity and authenticity**.

---

# 16. OAuth 2.0

OAuth 2.0 is an **authorization framework**.

The core idea:

> An application can access resources on behalf of a user without receiving the user's password.

Simplified flow:

```text
User
  ↓
Authorization Server
  ↓
Grant Permission
  ↓
Access Token
  ↓
Application
  ↓
API
```

Tokens can be:

```text
Scoped
Time-Limited
Revocable
Limited
```

### OAuth vs JWT

Don't confuse them:

```text
OAuth 2.0
    ↓
Authorization Framework

JWT
    ↓
Token Format
```

Therefore:

```text
OAuth ≠ JWT
```

OAuth can use JWTs, but they are fundamentally different concepts.

# 17. No Authentication

Some APIs are intentionally public.

Example:

```http
GET /api/weather/london
```

Public doesn't mean unrestricted.

A public API can still enforce:

```text
Rate Limiting
Request Restrictions
Other Controls
```

Remember:

> **Public API ≠ Unlimited API**

# 18. Authorization

Authorization answers:

> **What are you allowed to access?**

Suppose:

```text
User = user1
```

The backend might allow:

```text
View own profile      ✓
View own orders       ✓
Delete another user   ✗
Admin panel           ✗
```

The important flow is:

```text
Authentication
      ↓
Identify the user
      ↓
Authorization
      ↓
Check permissions
```

# 19. Business Logic

Business logic contains the **rules of the application**.

Examples:

```text
A user can view their own account
A coupon can only be used once
Only admins can delete accounts
Transfers cannot exceed a limit
```

Think:

```text
Authentication
    ↓
"Who are you?"

Authorization
    ↓
"What can you access?"

Business Logic
    ↓
"What should the application allow?"
```

These are **three different checks**.

Modern backends may be split into multiple services.

```text
                 API Gateway
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
 User Service    Order Service   Payment Service
        │             │             │
        ▼             ▼             ▼
    Database       Database       Database
```

For an online store:

```text
User Service
    ↓
Accounts

Order Service
    ↓
Orders

Payment Service
    ↓
Payments

Email Service
    ↓
Notifications
```

The client usually doesn't need to know these services exist.

# 24. Monolith vs Microservices

### Monolithic

```text
┌─────────────────────┐
│    ONE APPLICATION  │
│                     │
│ Users               │
│ Orders              │
│ Payments            │
│ Emails              │
└─────────────────────┘
```

### Microservices

```text

Orders    → Order Service
Payments  → Payment Service
Emails    → Email Service
```

The API consumer can interact with either architecture without necessarily knowing which one is behind it.

# 27. BOLA / IDOR

Suppose you're authenticated as:

```text
User 100
```

You request:

```http
GET /api/users/100
```

You receive your own data.

Now:

```http
GET /api/users/101
```

The security question becomes:

> **Is User 100 authorized to access User 101?**

If sensitive data is returned without proper authorization, this may indicate:

```text
BOLA
Broken Object Level Authorization
```

Also commonly referred to as:

```text
IDOR
Insecure Direct Object Reference
```

The key distinction:

```text
Authentication
    ↓
"You are User 100."

Authorization
    ↓
"Can User 100 access User 101?"
```

# 30. Encoding vs Encryption

### Encoding

Changes representation.

```text
Base64
URL Encoding
HTML Encoding
Unicode
```

### Encryption

Protects information using cryptographic keys.

Remember:

```text
Base64 ≠ Encryption
JWT ≠ Encryption
```

Encoded data can generally be decoded without a secret.

```text

       │ HTTPS
       ▼
┌──────────────┐
│ GATEWAY / WAF│
│              │
│ Routing      │
│ Filtering    │
│ Rate Limit   │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  API SERVER  │
│              │
│ REST/GraphQL │
│ AuthN        │
│ AuthZ        │
│ Validation   │
│ Business     │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│   DATABASE   │
└──────┬───────┘
```

